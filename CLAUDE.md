# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```sh
make db-up                # start dev Postgres (container, port 5433 — see below)
make dev                  # esbuild watch + Go server (-dev -seed) on http://localhost:8080
make -C dev/oidc up       # start the throwaway OIDC provider (dev/oidc; only starts/stops it)
make dev-oidc             # like `make dev` but with -auth=oidc against that provider
make test                 # Go tests (store tests need the compose DB, skip if DATABASE_URL unset) + frontend tests
make check                # go vet + tsc --noEmit
make build                # production binary (embedded frontend) -> bin/roadie
npm run --prefix web build   # rebuild frontend only (also copies index.html to dist)
npm run --prefix web test    # frontend unit tests only
```

Single Go test: `DATABASE_URL=postgres://roadie:roadie@localhost:5433/roadie go test ./internal/store -run TestItemInvariants`

Frontend tests use Node's built-in runner (`node --test`): `*.test.ts` files live next to their source, are transpiled by esbuild into `web/test-out/` (gitignored), and use `node:test` + `node:assert`. There is no browser/DOM test runner — test pure logic by extracting it into a DOM-free module (e.g. web/src/links.ts ← links.test.ts); exercise DOM/render code in a real browser instead.

Environment quirks (this machine):

- The dev DB is on **port 5433** because a native Postgres already owns 5432. Don't "fix" this back to 5432.
- Docker runs via colima; the Makefile deliberately uses the dashed `docker-compose` binary on macOS (`DC_CMD`) — the `docker compose` plugin is not wired up here.
- `make dev` serves `web/dist` from disk (`-dev` flag); production builds embed it via `go:embed` (web/embed.go). `web/dist/.gitkeep` must exist for the embed to compile.

## Architecture

Single-page roadmap editor. Guiding principle: **radically simple data model; all views are derived from it.**

Model (4 entities, see internal/store/migrations/001_init.sql):
`roadmaps` → `lanes` ("contexts", the swimlanes, ordered by `position`) → `items` (start/end DATE, nullable `parent_id`). Lanes also hold `milestones` (single DATE, title, description — see 005_milestones.sql): fixed points in time, no duration, no rank, not nested, not draggable.

Invariants are enforced in **internal/store** (not triggers, not handlers):

- Item nesting is at most one level deep (a parent cannot become a child; a child cannot gain children).
- A child's lane always equals its parent's lane; moving a parent to another lane moves its children too.
- Lane reorder (`PUT .../lane-order`) must list exactly the roadmap's lane IDs; positions are rewritten transactionally.
- Items carry an explicit `rank`: their position within their container (lane for top-level items, parent for children), kept **dense 0..n-1 per container** by the store on every create/move/delete. `PATCH /api/items/{id}` with `rank` means "insert at this index after removing me" (clamped; omitted rank on a container move = append). `POST` accepts a `rank` too — the same clamp-and-shift minus closing a gap in an old container, since a new item has none — so creating into a slot is one transaction under the roadmap lock rather than a create followed by a move. Omitted = append. The frontend relies on rank == array index.
- Lanes have a `color` theme (blue/green/red/orange/purple — validated in the store, auto-assigned round-robin by position on create). The frontend maps the name to a hex in web/src/colors.ts and sets it as `--c` on the lane element; **all** bar/tint/border shades derive from `--c` via CSS `color-mix` in styles.css — never hard-code per-color CSS.
- Vertical layout is one row per item (top-level and children alike), stacked in rank order (web/src/layout.ts) — pixel positions are never stored, only the order is.
- Milestones have no invariants beyond non-empty title + required date; the store keeps no ordering (they're read back ordered by date). They render as diamonds in a band at the lane top (web/src/render.ts), each with its title beside it, ellipsized by CSS against a `--avail` budget set from the gap to the next milestone (they arrive date-sorted) and hidden outright below `MS_LABEL_MIN` px. Hover/selection reveals the full title on a raised chip, which **replaced the native `title` tooltip** — its delay was the whole problem, so don't put one back. They share the item edit panel — selection is exclusive (`state.selectItem`/`selectMilestone`/`clearSelection`). CRUD is a separate REST surface: `POST /api/lanes/{id}/milestones`, `PATCH`/`DELETE /api/milestones/{id}`.

Backend: stdlib `net/http` (Go 1.22 method routing) + pgx, hand-written SQL. internal/server is a thin JSON layer: it maps `store.ErrNotFound` → 404 and `*store.ValidationError` → 400 via `writeErr`. All item moves (dates, lane change, reparent) go through a single `PATCH /api/items/{id}`; `model.Opt[T]` distinguishes absent JSON fields from explicit `null` (used for `parentId`). Migrations: numbered SQL files in internal/store/migrations, embedded, applied at startup by store.Migrate — add a new `00N_*.sql` file, never edit applied ones. store.Migrate splits two cases: a **fresh** database (empty `schema_migrations`) is built in one step from the consolidated internal/store/schema.sql, then all existing migrations are marked applied; an **existing** database gets the pending numbered migrations. So schema.sql is the readable source of truth for the current schema — whenever you add a migration, fold the same change into schema.sql. `TestSchemaMatchesMigrations` builds both ways in a throwaway namespace and fails if they diverge.

Frontend (web/src, TypeScript, no framework, bundled by esbuild):

- `state.ts` is the single client-side source of truth (subscribe/notify); every notify triggers a **full re-render** of the chart (render.ts) with scroll preserved. There is no virtual DOM and no partial updates — keep it that way unless item counts make it slow.
- `actions.ts` wraps every mutation: optimistic local apply (mirroring the server invariants in `applyItemPatch`) → API call → rollback + toast on failure. Creates are not optimistic (server assigns IDs). New items default to a `DEFAULT_ITEM_SPAN`-day length from today; a **new child** instead inherits its parent's exact start and end dates (`addItem`). `addItem`'s optional `rank` rides **on the create itself** (`NewItem.Rank`, an `Opt[int]` since rank 0 is a real slot), not a follow-up rank PATCH: a second request would leave a window for a concurrent create in the same container to land between the two, and would show every other session a create-then-move. The response's rank is then the authority for where to splice locally.
- `dnd.ts` is one pointer-event controller for all gestures (bar move/resize, vertical reorder, reparent, lane reorder via grip). Drop semantics: hovering a top-level item's **header `.bar`** = nest into it; anywhere else in a lane = insert as top-level at the pointer's vertical index (insertion line shown); a child over its own parent block = reorder among siblings. Drags manipulate element styles only as a preview; the model is updated once on drop through `actions.updateItem`. Drop targets are found with `elementFromPoint` while the dragged element has `pointer-events: none`.
- **Snapping** (dnd.ts) is the app's most delicate UX — treat it carefully. A dragged/resized edge magnetically snaps to nearby item edges, milestones, and today (within `SNAP_PX`), and otherwise to a user-selected calendar grid — day / week (Mon) / month (1st) / quarter — held in `state.snapMode` (persisted globally as `roadie.snap`, chosen via the magnet menu). Hold **Alt** to bypass both. Critically, snapping runs in the **boundary domain**: a bar owns pixels `[xOf(start), xOf(end+1))`, so edges snap on `start` and `end+1`, not `start`/`end` (`collectSnapBounds`, `snapBoundary`). That is what makes "A's end meets B's start" come out flush instead of overlapping by the shared inclusive day — keep any new snapping in this domain.
- `timescale.ts` converts ISO dates ↔ integer day numbers ↔ pixels; end dates are **inclusive** (a one-day item spans start==end; bar width = end − start + 1 days). `snapToGrid`/`weekStart`/`quarterStart` are the pure calendar-grid helpers (unit-tested in `timescale.test.ts`).
- Item titles that don't fit their (possibly very short) bar render **outside** it, to the right on the row background (`render.ts` `barOutside`) instead of truncating. The fit test measures the title with `canvas.measureText` (layout-free, no reflow) against the bar's pixel width. Each item owns its whole row, so that space is always free; the outside label is `pointer-events: none` (only its link re-enables clicks) so it never disturbs drag hit-testing.
- CSS-only layout tricks that are load-bearing: the chart is one scroll container with `position: sticky` for the time header (top) and lane labels (left); item bars are absolutely positioned inside `.lane-canvas`.

Snapshots (version history — "go back", not undo; internal/store/snapshots.go, internal/server/snapshots.go, web/src/history.ts): point-in-time copies of a roadmap stored as the export envelope (`model.RoadmapExport` JSON) in a **`bytea`** column (007_snapshots.sql) — deliberately not `jsonb`, since we only ever read whole blobs. `kind` is `'auto'` (retained by an **age-tiered downsample** in `pruneAutoSnapshots`, not a count cap: everything from the last 24h kept in full, then thinned to one per hour for the past week and one per day beyond — kept forever, since a small daily blob is cheap; the prune is a single `date_trunc(CASE …)`-bucketed `DISTINCT ON` and runs lazily on each auto capture) or `'manual'` (kept indefinitely, ignored by pruning; a nullable `name` — the naming UI is a deferred nice-to-have). The server auto-captures the affected roadmap **before** a mutation via the route-table `s.snap` wrapper (not scattered through handlers): throttled to at most one per `snapshotInterval` for edits, **forced** before deletes so each is individually recoverable; capture is best-effort (a failure logs, never fails the user's edit). Viewing is read-only: the client loads a snapshot's `RoadmapFull` (same shape as `current`) into `state.current` under a single **`state.preview`** flag — every mutation no-ops at that one flag (`actions.ts` `optimistic` + the three creates, `dnd.ts` gesture start) instead of threading a read-only flag through the render/menu code, and the edit panel steps aside. Restore replaces the roadmap's contents **in place** (same id); the store captures the pre-restore state first, so a restore is itself undoable.

Trash (soft delete for roadmaps; 011_roadmap_deleted.sql, `roadmaps.deleted_at`, internal/server/trash.go, web/src/trash.ts): deleting a roadmap **marks** the row instead of removing it, and `DELETE /api/roadmaps/{id}` is that mark. This was the one irreversible action in the product and the one place version history could not help: `snapshots.roadmap_id` is `ON DELETE CASCADE`, so a pre-delete snapshot would be destroyed by the very statement it was taken to survive — which is why the roadmap DELETE route is the only mutation not wrapped in `s.snap` (nothing to capture, nowhere for it to live; it does take `s.guard` for the access check — see Visibility). Nothing cascades on a mark, so lanes, items, milestones, schedule periods, snapshots *and* contributors survive and `RestoreRoadmap` is one `UPDATE` — restoring returns the roadmap with its full history. Two clauses do all the work: `deleted_at IS NULL` in **`getRoadmapFull`** makes a trashed roadmap unreadable — and therefore un-openable, un-exportable, un-duplicable and un-restorable-into, since every one of those paths reads through it — and the same clause in **`lockRoadmap`** freezes its contents, because every lane/item/milestone/schedule write takes that lock (by roadmap, lane or item id), so a stale second tab gets 404s rather than editing into the trash. Permanent deletion is a separate step and the store enforces it: `PurgeRoadmap` only deletes a row that is *already* trashed (`ErrNotFound` otherwise), so "two deliberate steps" is an invariant, not a UI convention; `DeleteRoadmap` (unconditional) survives only for tests and tooling. Retention is **30 days** (`trashTTL`), swept by `RunTrashSweeper` — blocking, so main owns the goroutine, and started there rather than in `New` so tests get no background writer of their data — sweeping on entry and then every 6h, in-process like the snapshot throttle (several replicas each sweep; the DELETE is idempotent). The TTL lives in the server, not the schema, because it is policy: `GET /api/roadmaps/trash` returns a `trashEntry` (roadmap + computed **`purgeAt`**) so the countdown the UI shows can't drift from the sweeper that acts on it. Frontend: the trash is a tab in the Home dialog (see below); Restore closes Home and opens the roadmap, since that is nearly always why you came, while a purge confirm stacks on top of Home as a nested modal and the list refreshes in place. The delete confirm names the trash explicitly — the reassurance is the whole feature, and it is worth nothing if the confirm still reads like the end of the world. Scope limit: the roadmap **list** isn't live (see Live updates), so another tab learns about a delete when it next loads.

Home (the roadmap dialog; web/src/home.ts, opened from the topbar "Home" chip — house icon + label, tinted in the favicon's brand indigo and deliberately the *only* colored control in the topbar; the brand wordmark next to it is deliberately *not* a second trigger — two adjacent buttons doing the same thing feel broken): every "which roadmap?" concern in one surface — picking, previewing, creating, importing, and the trash. It replaced three things: the picker dropdown, the "Roadmap info" dialog (info.ts, deleted — its facts/authors rendering was absorbed), and the standalone trash dialog (trash.ts, likewise). The core interaction is **select-then-act**: single click previews a roadmap in the sidebar (`GET` roadmap + contributors on selection, an out-of-order guard via `previewToken`), double click or the Open button opens it — deliberately *not* open-on-click, because the preview is the added value over a dropdown (identify a roadmap by its contents before committing), the speed argument is settled by the double-click shortcut, and the trash tab *needs* selection semantics anyway since a trashed roadmap cannot be fetched at all (404 by design — its sidebar shows only name, deletion stamp and days-left countdown). Home owns its own **`<dialog id="home-dialog">`**, not the shared `#dialog`, precisely so `promptDialog`/`confirmDialog` can stack on top as nested modals (HTML top layer) — the New prompt and purge confirm open over Home and return to it, no close-and-reopen dance. It rebuilds its whole DOM from module-local state on every change (mirroring the app's full-re-render principle) and forgets tab/selection on close; the roadmap list is refetched on every open, which is the moment non-live list changes from other sessions become visible. The topbar consequently slimmed to two honest affordances: a **house icon** opens Home (never disabled — with zero roadmaps Home is where New/Import/Trash live), and the **name button with the chevron is the actions menu** for the roadmap it names (rename, schedule, duplicate, export, history, delete — the former three-dot menu, which the name-as-trigger replaced; disabled when nothing is open). **New and Import moved into Home's footer.** Keyboard shortcuts already yield to it for free (keys.ts guards on any `dialog[open]`).

Schedule (Agile cadence — sprints/PIs; 008_schedule.sql, internal/store/schedule.go, internal/server/putSchedule, web/src/schedule.ts): a roadmap-level, flat list of named `schedule_periods` (`label`, inclusive `start_date`/`end_date`), roadmap-scoped like nothing else in the model — **not** under a lane. Like milestones they have no rank (read back ordered by `start_date`); the store enforces non-empty labels, `end >= start`, and **non-overlap** (gaps allowed). Deliberately **single track** (one row of periods, either sprints *or* PIs — not both nested); don't add multi-track without asking. It rides in `RoadmapFull.Periods` / the `RoadmapExport` envelope, so export/import and snapshots inherit it — but because it's roadmap-scoped, `RestoreSnapshot` must delete `schedule_periods` explicitly (the lane cascade doesn't reach it). Editing is a **full replace**: `PUT /api/roadmaps/{id}/schedule` (wrapped in `s.snap`), driven by a textarea opened from the roadmap's three-dot menu ("Edit schedule…" — it's roadmap data, not a snap setting; `START END LABEL` lines, parsed in the DOM-free `web/src/schedule.ts`). Snapping: `SnapMode` gains `"schedule"` (opt-in via the magnet menu, disabled until a schedule exists) — it swaps the coarse grid fallback in `dnd.ts` for the nearest period boundary (start / end+1, same boundary domain as item edges); it degrades to free placement on a roadmap without one. Display is tied to **existence, not snap mode**: when a schedule is present the header's **quarter row is replaced** by a band of positioned period spans (sparse — gaps are real, labels hidden below a px threshold with the full label on hover), the months row gains a 2-digit year ("Jan 26", since the quarter row otherwise owns the year), and the canvas gridline emphasis moves from quarter-starts to period boundaries.

Live updates (multi-user change notification via SSE; internal/server/events.go, web/src/events.ts): a roadmap open in one session is refreshed when another session edits it. The event is a **doorbell, not the data** — `{roadmapId, rev, origin}`, no payload; on receipt the client refetches the whole roadmap (`actions.refreshFromServer`, which preserves selection/scroll where the referenced rows survive). We deliberately **do not** diff over the wire: reimplementing `applyItemPatch`'s invariant logic on the receive path would be a second source of truth. Server side: an in-process `hub` (`map[roadmapID]→subscriber chans`) fanned out from a post-success broadcast **folded into the `s.snap` wrapper** (it already resolves the roadmap id *before* the mutation — needed, since a delete makes it unresolvable after — and a `statusRecorder` gates the broadcast on 2xx); `restoreSnapshot` broadcasts explicitly (not snap-wrapped). Sends are non-blocking with drop-on-full — a wedged client self-heals on the next event/reconnect. In-process means **single-replica** (like the snapshot throttle); the clean multi-replica upgrade is Postgres LISTEN/NOTIFY re-broadcasting into the same hub. Client side, two things are load-bearing: (1) **echo suppression** — each tab sends `X-Client-Id` on every request (api.ts), the hub echoes it as `origin`, and a tab ignores its own events; without it every field-save would refetch and blow away the editor under the cursor. (2) The **safe-gate** — a refresh replaces `state.current` and triggers a full re-render, which would yank a drag or destroy a focused input, so it's applied immediately only when safe (`isEditing()` = `state.preview` || `isDragging()` || the edit panel `contains(document.activeElement)`); otherwise it defers behind `state.stale` and the "Updated elsewhere · Refresh" pill, flushed on `focusout`/`pointerup`/pill-click. A burst gesture (parent-with-children move, multi-select nudge) sends N PATCHes → N broadcasts, but the receiver's ~250ms debounce (`scheduleRefresh`) collapses them to one refetch, so no server-side coalescing is needed at this scale. On EventSource *reconnect* (not first open) the client refetches once, to catch a change missed while disconnected. Scope limit: the roadmap **list** (create/rename/delete of roadmaps in the sidebar) is deliberately not live — only the currently-open roadmap's contents.

Authentication (internal/auth, `-auth` flag): two modes, and **the default is unchanged** — `-auth=off` means no login, everyone edits, `/auth/*` doesn't even exist, and plain `curl` against the API keeps working. `-auth=oidc` delegates login to an OIDC provider (Entra ID in production); there is **no password store, no user table and no session table**. The decoupling that keeps this from spreading: `auth.From(ctx)` **always** returns an `Identity`, anonymous when auth is off, so no handler ever branches on the mode — the only place that knows is `server.New` (via `server.WithAuth`). Roadie is a **confidential** client: the code flow (PKCE, S256) runs server-side and the browser only gets a sealed cookie, never a token. That is load-bearing for SSE — `EventSource` cannot set an `Authorization` header but does send cookies, so events.go needed no changes. The ID token is used once at the callback to learn who the user is, then **discarded** (no access/refresh token is kept: Roadie calls nothing downstream). Sessions are **AES-256-GCM sealed cookies** (`SESSION_KEY`, 32 bytes) holding `{sub, name, email, exp}` — stateless, so they survive restarts and work across replicas, unlike the SSE hub and snapshot throttle; the trade is no revocation before expiry. The pre-redirect flow state (state/nonce/PKCE verifier) rides in a second short-lived sealed cookie for the same reason. Identity claims are read from the ID token, falling back to **UserInfo** when it carries nothing but `sub` — that is not a mock quirk but standard OIDC (IdentityServer withholds them unless the client sets `AlwaysIncludeUserClaimsInIdToken`; Entra inlines them), and without it attribution degrades to an opaque subject id. Several claim spellings are accepted (`name`, `preferred_username`, `upn`, `email`) because the provider decides which it emits. A UserInfo failure is logged, not fatal: the subject alone still identifies the user. Config: `-auth`, `-oidc-redirect-url` (**configured, never derived from the Host header**, so no proxy header is trusted; its scheme decides the cookies' `Secure` flag, and its **path is where the callback route is served** — the provider's registered URI is often not ours to choose, so it must not be a fixed `/auth/callback`), `-session-ttl`, `-oidc-insecure-tls` (headless/scripted flows against a self-signed mock only — it relaxes **Roadie's** client, and cannot help a *browser*, which connects to the provider itself; point local dev at a mock's plain-HTTP endpoint instead, which is what `make dev-oidc` does); secrets come from the env (`OIDC_ISSUER`/`OIDC_CLIENT_ID`/`OIDC_CLIENT_SECRET`/`SESSION_KEY`) since flags are visible in `ps`. Diagnosing a new provider: the login line always reports **which claim won** (`name<-preferred_username email<-none`, plus `userinfo=true/false`), because a tenant that fills `name` with an object id is a *success* path with no error anywhere; `-auth-debug` (or `AUTH_DEBUG=1`, so a container can be toggled with `oc set env` rather than by editing its args) additionally dumps **every** claim from the ID token and UserInfo, which is the only way to see claims `userClaims` doesn't parse — off by default, since claim values are personal data. Deny by default: everything is gated except `/healthz`, `/readyz` and `/auth/*` (`publicPath`). The challenge is **content-negotiated** — an HTML navigation gets a 302 into the flow, an XHR/EventSource gets 401, because redirecting those to the provider only surfaces as an opaque CORS error; the client turns 401 into a navigation (`api.ts` `toLogin`), and events.ts probes `/api/me` after a persistent SSE outage since `EventSource` retries silently forever on 401. CSRF: `SameSite=Lax` is the main defence (and is required anyway for the callback redirect to carry the state cookie), backed by `requireClientHeader` — the `X-Client-Id` header that already rides on every request for echo suppression can't be set cross-origin without a preflight, and no CORS headers are served. It is installed **only with auth on**, since an open deployment has no ambient authority to forge. Logout is local only (no RP-initiated logout: ending the Entra session would sign the user out of every company app) and lands on `/auth/signed-out` rather than `/`, where the login redirect would silently re-authenticate and make the button look broken. Frontend: `/api/me` returns `{mode}` so the UI learns the deployment's mode at runtime — in `open` mode the account menu stays hidden and nothing else differs. Attribution rides on that identity — see Contributors below.

Visibility and access (private vs. public roadmaps; 012_roadmap_visibility.sql, internal/store/access.go, `s.guard` in internal/server/snapshots.go, web/src/dialogs.ts `newRoadmapDialog`): a roadmap is `public` (the default — everyone may see **and edit** it, exactly as before this existed) or `private` (only the subjects in `roadmap_members`). There is deliberately **no read-only sharing**: public means writable, so this is a visibility axis, not a permission system. The whole model is **one predicate**, `visibleExpr`: `visibility = 'public' OR subject ∈ roadmap_members`. It is phrased against a *subject*, never against "is auth on?", and that is what keeps the feature from spreading: `auth.From` always yields an Identity whose subject is `""` when anonymous, and the schema forbids an empty subject (`CHECK (subject <> '')`), so an anonymous caller structurally matches no membership row. With auth off no private roadmap can be created either (the store rejects `private` with no owner — an **identity** check, not a mode check), so every roadmap is public and the predicate is trivially true. Exactly one thing in the product depends on who is asking rather than what they are asking about, and even it is that same identity check. The reverse transition is fail-closed by choice: an oidc deployment restarted with auth off hides its private roadmaps from everyone, because the alternative — letting anonymous see everything — is the mode branch in the one place it must never be. Where the check lives is the deliberate **asymmetry with the trash**: that one is two `deleted_at IS NULL` clauses in the *store* (`lockRoadmap`, `getRoadmapFull`) because it needs no caller, whereas access does, and the store has callers with no user at all — the trash sweeper, seeding, snapshot capture/prune, and the internal `getRoadmapFull` behind export and duplicate — so a store consulting the request identity would 404 its own background jobs. Instead the server checks once per request in **`s.guard`**, which reuses the resolvers `s.snap` already had (`byRoadmapID`/`byLaneID`/`byItemID`/`byMilestoneID`, plus a new `bySnapshotID`): they already answer *which roadmap does this request touch*, which is exactly authorization's question. Authorization is **folded into `s.snap`** rather than composed around it, so a mutating route cannot be wrapped for snapshots but not for access. Denials are **404, not 403** (a roadmap you can't see doesn't exist — same as a trashed one, and it blocks existence probing), and an *unresolvable* roadmap falls through to the handler so the pre-existing 400/404 statuses are unchanged. Two routes can't be wrapper-shaped and filter in SQL instead — `ListRoadmaps`/`ListTrashedRoadmaps` are the only store methods taking a viewer, because a listing has no id to check; `create`/`import` have nothing to authorize yet. What replaces the store-level guarantee we gave up is **`TestEveryAPIRouteIsClassified`**, which reads the route patterns back out of server.go and fails unless each `/api/` one is either exercised by the 404 sweep (`TestPrivateRoadmapIsUnreachable`, every route × outsider + anonymous) or listed as exempt with a reason — so authorization can't be lost by omission. Ownership: the creator is recorded as `role='owner'` for **public roadmaps too** (access ignores it there; it answers *who may change visibility*), enforced single by a partial unique index. Only the owner may flip visibility (`PUT /api/roadmaps/{id}/visibility`, its own route since visibility is **not roadmap content**); a roadmap with **no** owner — anything predating this, or created with auth off — can therefore never change and is public forever, which is a consequence of the rule rather than a special case. `role` already allows `'editor'` so sharing widens a CHECK instead of adding a column. By the restore test, visibility and membership are **not** content: they ride in the snapshot blob only because `Roadmap` is embedded in `RoadmapFull`, and `RestoreSnapshot`/`ImportRoadmap` ignore them exactly as they ignore ids and timestamps — a file must not publish itself, and restoring January must not republish what you made private in June. `uniqueRoadmapName` is scoped to the *visible* set for the same reason: renaming your import to "(2)" because of a stranger's private roadmap both misbehaves and discloses a name. Duplicating inherits the source's visibility (a copy of a private roadmap isn't published) but takes the copier as owner. `model.Roadmap.Owned` is derived per request and `omitempty`, so a subject never reaches the browser (as with `Contributor.Subject`) and it never lands in an export. Frontend: `state.me` exists solely so the New dialog offers "private" only where it can be honoured; everything else reads `visibility`/`owned` off the roadmap, so no UI code branches on the auth mode. A padlock marks private rows in Home (public is unmarked — it's the common case), the preview sidebar gains a "Visible to" fact for private ones only, and the roadmap actions menu grows a Make private/Make public entry that is hidden unless `owned` and sits **below Version history**, with the rare operations. **Both directions confirm**: publishing obviously must, but so does locking down — it is trivially undoable yet just as easy to misclick, and a roadmap that silently disappeared from everyone else's list is a problem nobody knows to look for. Neither is destructive, so both use the neutral confirm button. Scope limits, both deliberate: **Import always creates a public roadmap** (the owner is recorded, so it can be flipped immediately afterwards), and changing visibility does **not** broadcast over SSE, so another tab already viewing a now-private roadmap keeps its stale copy until it refetches.

Contributors (who worked on a roadmap; 009_contributors.sql, internal/store/contributors.go, internal/server/contributors.go, the header block in web/src/history.ts): one row per person per roadmap — `subject` (the OIDC sub, the row key), a denormalized `name`, `first_seen`, `last_seen`. Deliberately **a set of people, not an audit log** and **not a counter**: an "edit" here is one PATCH, and a burst gesture (parent-with-children move, multi-select nudge) sends several, so any count would measure who drags big parents around rather than who did the work — and once displayed a count reads as a productivity metric it cannot support. Ordering is **alphabetical by name** for the same reason; an activity order invites reading the list as a ranking. The write hangs off the existing `s.snap` wrapper (after the handler, behind the same `rec.status < 300` gate as the SSE broadcast, so a rejected edit credits nobody) and is **best-effort** like the snapshot capture — attribution must never fail a user's edit. Four routes can't use the wrapper and call `recordContributor` explicitly: `restoreSnapshot` (a restore is an edit like any other), and `createRoadmap`/`importRoadmap`/`duplicateRoadmap` — `snap` resolves the roadmap id *before* the handler, and for those the id doesn't exist yet (for duplicate, the path id is the **source**, so wrapping it would credit the wrong roadmap). Without those three the creator of a roadmap would surface only once they edited something inside it. With `-auth=off` the identity is anonymous, nothing is written, and the UI hides the block — open mode looks exactly as before. The name is refreshed on every edit (last write wins) because there is no user table to re-read it from, and `subject` is `json:"-"`: the browser only ever sees names. The load-bearing decision is that contributors are **editing metadata, not roadmap content**, so unlike `schedule_periods` they stay out of `RoadmapFull`/`RoadmapExport` and `RestoreSnapshot` leaves the table **untouched** — restoring January must not un-person whoever edited in June. The general test for any new roadmap-scoped field: *if I restore this snapshot, should this data revert too?* Yes ⇒ it belongs in the envelope; no ⇒ it gets its own endpoint, as `GET /api/roadmaps/{id}/contributors` does (fetched on demand, not on roadmap load). Two surfaces consume it: the history sidebar shows **only the last editor** (the full list is unbounded and buries the version list in a 280px column), and the **Home dialog's preview sidebar** (web/src/home.ts) shows the full per-author `first_seen`/`last_seen` table alongside the roadmap facts — fetched per selection, since Home previews roadmaps that aren't the loaded one. The facts are chosen to *distinguish* roadmaps, not to inventory them: timespan (`contentRange`), **last edited** (derived as max `last_seen` over the contributors — `roadmaps.updated_at` can't answer this, it only moves on rename/restore), created, the context **names** (not a count — the nearest thing to a table of contents), one compact size line, a flagged count only when nonzero, and the schedule shown as "Standard" (plain calendar grid) vs. "n periods".

Flags and focus (010_item_flagged.sql; `items.flagged`, web/src/keys.ts, `flagMark` in render.ts, `flagButton` in panel.ts): one boolean per item — a single **product-defined** "needs attention" marker, rendered as an amber ⚑ outermost on the bar. The history here matters: user-colored **stars were rejected** because the user supplies the meaning at mark time and nothing records it (a yellow star means nothing next week, and a second person's blue star means less), which is why free-form **labels** plus a focus/dim toggle came first. Labels are semantically sound but invisible on the bar, so there was still no way to mark "these five have a problem" mid-discussion. The flag fixes exactly that gap by **owning its meaning in the product**: one flag, one glyph, nothing to look up — the edit panel's icon-only toggle carries the whole legend in its tooltip ("Flag: needs attention"), which is affordable only because there is exactly one flag with one meaning. It shares the priority row rather than owning a `panel-field` of its own: it is an item attribute like priority, and a lone toggle isn't worth a row. Never add a second flag or a flag color: two markers with user-assigned meanings *is* the star problem again. It was deliberately **not** implemented as a reserved `"flagged"` label, even though that would have reused the whole focus machinery for free: labels are free-form text, so a magic string is a convention and not an invariant (nothing stops `Flagged`/`FLAG`/a user's own tag); it would surface in the label editor as a deletable text chip, needing filters in the chips, the datalist, and the commit path; and toggling would mean a read-modify-write of the `labels` array, which under SSE live editing loses a concurrent label edit — precisely during the fast burst usage the flag exists for. `Opt[bool]` patches are independent and commutative instead. There are **no invariants**: flagged is orthogonal to nesting/rank/lane and does **not** propagate between parent and child (a problem lives in one item), so the store just writes it. There is deliberately **no `flagged_at` and no flag note** — the note's job is done by the item description, and a timestamp nobody looks at is not worth a column; the guard against flag rot is instead that the focus menu's pinned **"Flagged (n)"** row is both the filter and the only place the total shows, since flags nobody can see never get cleared. It **is** roadmap content by the restore test above (it rides in `RoadmapFull`/`RoadmapExport`, so export/import and snapshot restore inherit it — unlike contributors). Focus is now a tagged union (`state.Focus` = one label **or** the flag, exclusive, `isDimmed(item)`), not a bare string, so a user's label literally named "flagged" can never act as the flag (unit-tested in state.test.ts). Milestones carry neither labels nor a flag, so any active focus dims them all. Two render gotchas: the glyph is `pointer-events: none` like the priority pill (flagging happens in the panel or via the shortcut, never by clicking it, so it can't swallow a drag), and `titleFits` must reserve `FLAG_RESERVE` px or short bars mis-measure and the flag overlaps the title. `--flag` is intentionally **outside** the lane themes and not derived from `--c`: an attention marker has to read the same against all five lane colors.

Keyboard shortcuts (web/src/keys.ts): **a single registry** — one window listener over one `bindings` table (`Esc`, `Del`, `n`, `c`, `!`), which the Help dialog also renders, so a new binding documents itself. Single-key only, no chords; `key` matching is case-sensitive (the field comment explains the Caps Lock trade). Two guards apply to **every** binding, which is the reason they live here rather than per handler: they don't fire in text fields unless they set `inTextField` (only `Esc` does), and all of them yield to an open `<dialog>`. Commands live in panel.ts beside the buttons they mirror (`deleteSelection`, `addItemToSelection`, `addChildToSelection`, `toggleFlagSelection`), never as a second implementation. The rule for what they act on: **per-item** operations apply to a whole multi-selection (`Del`, `!`), **positional** ones need exactly one target and silently no-op otherwise (`n`, `c`). Multi-delete is reachable only from the keyboard, since the edit panel — and its Delete button — shows nothing while several items are selected; one prompt (`confirmAndDeleteItems`) serves both counts so the wordings can't drift, and it counts cascaded children, which the selection alone doesn't show. `n` creates in the selection's own container — a child yields a sibling child, a top-level item a top-level sibling, a milestone a plain item in its lane — inheriting the selection's dates, landing **directly after it**, then focusing the new title so `n` → type → `Enter` is one flow. `c` creates a child item inside a selected top-level item, appending to its children array and focusing the new title so `c` → type → `Enter` is one flow; since nesting is one level deep, `c` no-ops on a selected child or milestone. `addSiblingOf` and `addChildTo` in panel.ts are the single implementations behind `n`/`c` and the panel's "Add Sibling"/"Add Child" buttons, so keyboard and mouse cannot drift apart; only a create with no anchor item appends (the lane's `+`, "Add Child", and `n` on a milestone).

Verification: beyond `make test`/`make check`, UI changes should be exercised in a real browser — **by the user, by hand**. There is deliberately no browser automation here: the maintenance cost of keeping playwright scripts working against this UI outweighs what they catch. Don't add one (or reach for a headless driver ad hoc) without asking first. When a change needs eyes on it, say so and describe what to look at.
